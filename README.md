# 龙脊少年 · 守约

> 一部**纯离线单机**的中世纪暗色奇幻「文字冒险 + 卡牌战斗」网页游戏。
> 无框架、无构建工具、无后端 —— 用 **HTML + CSS + 原生 ES Module** 直接在浏览器里跑,由 GitHub Pages 静态托管。

你扮演一名在焚村之夜失去家园的少年,握起父亲留下的旧剑「守约」,穿越剑塔、王城、渔港与云端浮岛;
在剑术、星图、风翼、盐风与信仰之间一次次抉择,最终决定 —— 你想成为谁。

- **玩法**:多章主线 + 支线剧情(4 种主结局)、地区地图探索与跨区远行、卡牌构筑战斗、商店 / 市场 / 密市经济、主城六设施、打工小游戏、宝箱解谜、NPC 闲谈、邮箱与兑换码
- **形态**:纯静态站点,无后端、无注册、无内购、无广告;进度只保存在本机浏览器
- **体量**:约 4.7 万行 JS、77 个章节模块、1135 个剧情节点、280 件物品、56 张卡牌、53 种敌人

## 一、游戏搭建思维、结构与组成部分

### 1.1 搭建思维(设计哲学)

整个项目围绕四条主线展开:

| 思维 | 落点 |
| --- | --- |
| **内容数据化** | 剧情、物品、邮件、兑换码、条款文本全部是可编辑的数据模块;往数组 / 对象里加条目即可扩充,逻辑代码不动 |
| **逻辑与表现解耦** | 以 `EventBus` 为中枢,UI 只负责「渲染 + 抛事件」,`Game` 只负责「收事件 + 改状态」,双方不互相直接调用 |
| **快照式渲染** | 每个视图都由「当前状态」整体重绘,避免增量更新造成的状态漂移(UI 缓存 DOM 引用后一次性重建列表) |
| **纯静态可托管** | 没有服务器、没有打包、没有依赖树;`git push` 即上线,刷新缓存靠统一的 `?v=` 版本号 |

叙事侧的核心抽象是**「地区 → 地点(stop) → 剧情节点(node)」三段式**:
地图上的每个地点是一个锚点,章节文本按地点切段;引擎在锚点暂停,玩家必须真的在地图上走到该地点,才能触发这一段剧情。
这套「门控(gate)」机制把「走地图」和「读故事」缝在了一起,而不是两条平行线。

### 1.3 组成部分(系统模块)

- **剧情系统**:章节节点数据 + `engine.js` 门控推进。节点支持分支选项、战斗胜负跳转、职业分支、跨章引用(`ch02:n12`)、结局标记。
- **地图 / 旅途**:50 个地区、11 座主城;地区内有地点卡,跨区远行按真实秒计时并消耗行动力;载具改变地形通行与耗时。
- **战斗系统**:回合制卡牌战斗,能量 + 魔力双资源,状态效果(易伤 / 虚弱 / 脆弱 / 力量)、护甲、群体作战(多敌人 + 队友)、宠物协战、自动战斗。
- **经济系统**:商店 / 市场(收管理费)/ 密市(特殊交易币)三套价格体系;背包格数扩展;装备与外观;宝石镶嵌。
- **主城设施**:酒店(休息/回血/换装/回看/服务生跑腿)、酒馆(购物/请客/角斗/打工)、神秘商店(高价限定珍品)、银行(定期存款与汇率)、交易所(行情投资)、仓库(计费寄存)。
- **成长系统**:职业(多职介与等级)、装备与套装、宝石与「神话三件套」、宠物(常规 / 稀有 / 神话)、图纸锻造。
- **元系统**:年龄与内容警告门、邮箱、兑换码、存档、设置(音量 / 注销)、关于与合规文档。

## 二、AI 使用过程 · 调用的 API · 遇到的问题与解决

### 2.1 AI 使用过程

本项目绝大部分代码与文本在 **Trae IDE 的编码智能体(TraeCode)** 协助下完成 —— 仓库 95 次提交中有 **93 次的作者是 `Trae`**。典型协作流程是:

1. **提需求**:用自然语言描述玩法或修复点(例如「为 11 座主城增加酒店/酒馆/神秘商店/银行/交易所/仓库」)。
2. **读代码定位**:AI 先检索现有实现(模块导出、事件名、数据表结构),确认改动边界,再动手。
3. **改代码**:新增数据模块 / 扩展逻辑 / 渲染面板,并保持既有的数据化与事件总线风格。
4. **自验证**:对核心逻辑跑 Node 无头断言(见 2.4),对全部文件跑语法检查。
5. **提交推送**:确认无误后 `git commit && git push`,并按需升级全局 `?v=` 版本号。

两种常见的交互入口:

- **对话式开发**:在 Trae IDE 里直接描述要做什么,AI 端到端改完并验证。
- **分享链接纠错**:把 Trae 分享链接(`share.traecontent.cn/share/...`)里的错误点交给 AI —— AI 据此定位根因并修复(例如 ch27 剧情不推进、地图地点锚点错位等)。

### 2.2 AI 调用 / 涉及的 API

| API | 用途 | 说明 |
| --- | --- | --- |
| Trae 内置生成式模型 | 文本与代码生成、需求理解、代码检索与修改 | 开发期主力 |
| 文生图 API | 章节插图 / 图标的生成 | 端点形如 `https://trae-api-cn.mchost.guru/api/ide/v1/text_to_image?prompt=…&image_size=…` |
| GitHub API(`gh` CLI / GitHub 连接器) | 提交、推送、仓库操作 | 推送在沙箱中通过已授权令牌完成 |
| Node.js 内置模块(`fs` / `path` / `url`) | 开发期无头验证:临时目录复制、去 `?v=`、`import` 各模块做断言 | 不联网 |
| Google Fonts | 运行时唯一的外部请求,加载 `Noto Serif SC` | 可被屏蔽,字体回退为系统衬线体 |

> **重点**:游戏**运行时是纯离线的** —— 除 Google Fonts 外不调用任何后端 API,不采集、不上传任何数据。

### 2.3 AI 搭建过程中遇见的问题与解决方式

| # | 问题 | 根因 | 解决方式 |
| --- | --- | --- | --- |
| 1 | **章节重构后地图锚点错位** —— 玩家走到正确地点却不触发剧情(如 ch27 找不到 `n05` 节点) | `regions.js` 的 `stops[].node` 仍指向旧稿节点,章节合并后编号变了 | 逐处改锚到真实节点;再写校验脚本模拟引擎门控规则,对全部 50 个地区做指针一致性检查 |
| 2 | **单段落节点的选项被永久锁死**(选项 `opacity:0; pointer-events:none`) | `ui.js` 渲染顺序颠倒:先启动逐段渐显、后补加 `is-waiting`;而单段落节点的渐显会同步收尾并移除该类,随后又被补加,再无人移除 | 把「标记等待」前移到渐显之前;一处修复覆盖 35+ 个同路径节点(包括各章结局) |
| 3 | **沙箱内浏览器无法访问本地服务** | 远程沙箱访问 `localhost` 返回 `Unauthorized` | 放弃在线实测,改为 **Node 无头 import** 直接对各模块做单元 / 集成断言 |
| 4 | **ES Module 的 `?v=` 后缀导致 Node 无法解析** | `import './x.js?v=20261007r'` 在 Node 里不是合法路径 | 把 `js/` 复制到临时目录,`sed` 去掉查询串,加 `{"type":"module"}` 后再 `import` |
| 5 | **行动力上限语义偏差** | 初版只对「基础上限」封顶 100,装备加成仍可突破 | 按需求改为**总上限硬封顶**:`apCap() = min(100, apMax + 装备加成)`,并让加点上药返回「有效上限」的实际上升,已满则不消耗 |
| 6 | **数值边界难以肉眼验证**(1e10 金币、0.03% 概率、越买越贵) | 数值极端、概率极低 | 用大样本统计(6 万轮抽样、实测命中率 ≈ 0.0306%)与边界断言(0/1/2/3 颗宝石的套装行为)兜底 |
| 7 | **防具镶嵌逻辑存在但无 UI 入口** | `socketArmorGem` 已实现却无人调用 | 在精益师面板补上「武器 / 防具」分组与镶嵌 / 取下流程 |
| 8 | **整包发放奖励会把背包挤爆** | 一次性发数百种物品,超出初始格数 | 发放后自动把背包容量撑到「已持有格数」,避免后续无法收入新物品 |

### 2.4 AI 产出的验证手段

- **语法体检**:对全部 `.js` 逐个 `node --check`。
- **无头断言**:把模块导入 Node,直接验证行为,例如
  - 药品「越买越贵」:1 次 5000 → 5750 → 6612 …,并验证存 / 读档后价格能按次数复原;
  - 神话三件套:1 / 2 颗无效果、3 颗齐备时 `护甲+120 · 战力+120 · 每回合回魔+30 · 生命+300`;
  - 神秘商店稀有宝石:6 万轮抽样实测出现率 ≈ 0.03%;
  - 兑换码:金币 1000 亿、9 种交易币各 100 万、271 种道具各 1000、19 只宠物全部到手。
- **剧情校验脚本**:仓库内 [`verify-chapters.mjs`](verify-chapters.mjs) 做节点引用完整性、从 ch01 的 BFS 可达性、死节点与结局 flag 检查。

## 三、其他重要内容

### 3.1 本地运行

项目是原生 ES Module,**不能直接双击 `index.html`**(`file://` 下模块会被浏览器拦截),需要一个静态服务器:

```bash
# 任选其一,在仓库根目录执行
python3 -m http.server 8080
# 或
npx serve .
```

然后打开 `http://localhost:8080/`。调试时可在控制台使用 `window.__game`,例如 `__game.startNewRun()` 直接开一局、`__game.startNewRun('种子')` 复现随机序列。

### 3.2 部署

纯静态托管:**GitHub Pages**。部署仓库为 `wanderwrs/game-2026-kapaidashi`。
推送 `main` 分支即发布,无需构建步骤。

### 3.3 缓存与资源版本号

所有相互 `import` 的模块、样式与入口脚本共享同一个 `?v=YYYYMMDDx` 版本号(当前 `v=20261007r`)。
每次改动后统一升一位字母,即可让浏览器与 CDN 立刻拿到新资源,避免「改了没生效」的假象。

```bash
# 批量升级版本号的惯用做法
grep -rlZ 'v=20261007r' js index.html | xargs -0 sed -i 's/v=20261007r/v=20261007s/g'
```

### 3.4 存档与隐私

- 纯前端,无账号、无后端、无 Cookie、无埋点。
- 进度仅存于本机 `localStorage`,键名:`longji.fullstate.v1`(完整存档)、`longji.progress.v1`(章节进度)、`longji.music.v1` / `longji.volume.v1`(音量)、`longji.tutorial.v1`(引导)、`longji.mail.v1`(邮箱与已用兑换码)。
- 清除浏览器数据 / 换设备会丢档;游戏内「设置 → 注销」可一键清空本机进度。

### 3.5 合规与适龄

- 入口设 **18+ 年龄提示 + 内容警告 + 真人验证门**(按住 3 秒),每次打开页面都需通过。
- 内置完整文档:`关于` 弹窗涵盖游戏介绍、AI 生成声明、适龄提示、隐私协议、数据与存档、用户协议、安全声明、心理健康声明、生理健康建议、设计架构、免责声明、版权与许可、联系方式 —— 全部内容由 [`js/data/about.js`](js/data/about.js) 驱动。

## 四、总结

《龙脊少年 · 守约》是一次「**用最朴素的技术栈,承载尽可能厚的玩法与叙事**」的尝试:

- 技术上,它刻意**不引入框架与构建**:事件总线解耦、快照式渲染、内容全数据化 —— 这让一个体量不小的游戏依然能靠静态托管一键上线,也让任何一处内容都能被单独替换。
- 内容上,它以「地区 → 地点 → 剧情节点」的门控机制,把地图探索与剧情推进缝成一体,再用卡牌战斗、经济与设施把这条主线撑出厚度。
- 流程上,它验证了一种可行的 **AI 协作开发范式**:自然语言提需求 → AI 读代码定位 → 改动 → **无头验证 + 语法体检** → 提交推送。其中最有价值的部分,是「每改必验」的纪律 —— 用可复现的断言替代肉眼确认,才敢让 AI 去动一个 4.7 万行、1135 个剧情节点的项目。

AI 显著加速了「把想法变成可玩版本」的过程,但**取舍与验收仍然是人的工作**:数值是否合理、语义是否符合预期、哪些改动该做、哪些该拦住,都需要开发者逐处拍板。本项目的经验是:**让 AI 干它擅长的体力活(检索、批量改写、补全、自测),把判断权和最终审阅握在自己手里。**
